Tooling & CI

living document · maintain by hand
.github/ · scripts/ · .pre-commit-config.yaml

Purpose

This is the automation layer: two GitHub Actions workflows, one pre-commit hook, four Python scripts, and the thin Jekyll layer GitHub Pages insists on. The site itself is hand-written HTML with no build step, so everything here exists to do one of two jobs — keep generated files (sitemap.xml, feed.xml, log pages, timestamps) honest against their sources, and make the published track record impossible to revise after the fact. When something on the site looks like it "updated itself", the answer is in one of these files.

How it works

validate-track-record.yml — the integrity guard

Fires on push and pull request, but only when one of four paths changes: data/track-record.json, the two scripts that touch it, or the workflow itself. That path filter is the attack surface as well as the trigger — the workflow watches its own definition so a "harmless" CI edit cannot weaken the check unseen.

Three design rules, each of which exists because the naive version had a working bypass (all reproduced in commit fb61b8d before being fixed):

  • Reject force-pushes — in two layers, because one is not enough. The workflow's first step checks github.event.forced and exits 1. But the workflow is path-filtered, so a force-push that leaves the watched files' final content untouched fires no run and no rejection. The durable guard is branch protection on main (force-pushes and deletion disabled, enforced for admins — enabled 2026-09-03). Rewriting history destroys the timestamp trail the record rests on, and no file-level check can detect it after the fact.
  • Walk the whole range, not one hop. A push of N commits fires one run at the tip, so comparing HEAD to HEAD^ let an earlier commit in the same push tamper unseen. The workflow resolves a baseline ref (github.event.before on push, the PR base SHA on pull requests, merge-base with the default branch for new branches) and passes it to validate_track_record.py --check-append-only --ref, which inspects every commit in the range and then the working tree. fetch-depth: 0 is load-bearing — a shallow clone cannot see the pre-push commit.
  • Fail closed. If the baseline cannot be read — git missing, ref unresolvable, baseline JSON corrupt — the validator exits 2 ("could not run"), never a silent pass. Exit codes: 0 ok, 1 validation failed, 2 could not run.

The schema itself (fields, modes, immutable metadata) is documented in the track-record data contract page; the point here is that enforcement lives in CI, not in local tooling. append_observation.py validates before writing, but it only sees the file in front of it — a locally tampered file appends cleanly and is rejected on push. That split is deliberate: local tooling is convenience, CI is the guarantee.

build-site.yml — the rebuild bot

Two jobs, one workflow, triggered by pushes to main and pull requests that touch HTML, content/log/**, the generated metadata files, scripts/build_site.py, or the workflow itself:

  • check (pull requests only) runs python3 scripts/build_site.py --check, which exits 1 if any generated file is stale. A reviewer sees drift before it merges.
  • rebuild (push to main only, with contents: write) runs the generator for real, then commits as github-actions[bot] with the subject chore: rebuild derived site metadata. This is what rescues a page edited directly in the GitHub web UI — it still ends up with a correct lastmod instead of a silently stale one.

Two contracts hold this loop together, and both were bugs once:

  • Stage before diffing. The commit step does git add -A then git diff --cached --quiet. The original version diffed the working tree first; git diff ignores untracked files, so a newly generated page (a log entry added through the web UI) read as "nothing to rebuild" and was never committed. Fixed in the 2026-09-02 audit pass (a73f908).
  • The BUILD_COMMIT_SUBJECT contract. build_site.py computes every timestamp from the last commit to touch the file, excluding commits whose subject is chore: rebuild derived site metadata (the constant BUILD_COMMIT_SUBJECT, scripts/build_site.py:57). The workflow's commit step must use exactly that subject. Change one side without the other and the build chases its own tail: stamping a date changes the file, which changes its last-commit date, which demands another stamp, forever.

The pre-commit hook and the re-stage dance

.pre-commit-config.yaml defines a single local hook — python3 scripts/build_site.py with pass_filenames: false and always_run: true — so every commit regenerates derived files regardless of what was staged. It is opt-in (pip install pre-commit && pre-commit install, per the README) because pre-commit installs are per-clone.

The gotcha: when the hook rewrites files, pre-commit fails the commit because the working tree changed mid-commit. You must git add the regenerated files and run the commit again so the generated changes land in the same commit as their sources. That is expected behaviour, not a broken hook — the alternative is a commit whose sitemap disagrees with its content, which the CI check job will catch anyway.

journal_prompts.py — the 04:00 writing prompt

journal-prompts.html is a local morning-writing tool, not site content: it carries noindex and is excluded in _config.yml, so it never publishes. A launchd job (com.bradlasater.journal-prompts, scheduled at 04:00 local) runs scripts/journal_prompts.py, which scans the last 48 hours of commits in two repos — this one and the sibling data_ingest_infra — groups them per repo per day, and rewrites the table between <!-- PROMPTS:BEGIN --> / END markers plus the GENERATED stamp. Commits whose only changes are log entries (or the derived feed.xml/sitemap.xml) are skipped — an entry about an entry is noise. Dirty working trees get an "uncommitted" row, and no activity is a valid row: "no surprise, no entry" is the rule the page teaches. Missing markers fail loudly rather than clobbering the hand-authored guide around the table.

The Jekyll layer: _config.yml and CNAME

GitHub Pages runs Jekyll over the repo by default. The site is plain HTML with no templating, so _config.yml has exactly one job: keep source and tooling out of the published site via its exclude list — content, scripts, notes, data/SCHEMA.md, README.md, ROADMAP.md, journal-prompts.html. This is discoverability, not tidiness: without it, the log-entry fragments in content/ are served as broken half-pages at their own URLs, competing with the real entry pages they generate. If you add a new top-level source directory, add it here too. CNAME is one line — bradlasater.com — and is what makes Pages serve the custom domain; delete it and the site silently reverts to the github.io URL.

Conventions and gotchas

  • Every actions/checkout uses fetch-depth: 0. Timestamps and the append-only walk both read git history; a shallow clone silently invents wrong dates or an unverifiable baseline. Do not "optimise" this away.
  • The workflows are path-filtered. A push touching only assets/ or docs/ fires neither of them, which is usually what you want — but it means the rebuild bot is not a safety net for pages outside its trigger list.
  • build_site.py renders month names from a fixed table, not the locale — a non-English dev machine would otherwise render different strings than CI and desync --check.
  • journal_prompts.py assumes data_ingest_infra exists as a sibling checkout; a missing repo is skipped, not an error. Its launchd job lives on Brad's machine — a fresh clone has neither the hook nor the schedule until you install them.
  • Exit-code discipline across all four scripts: 1 means "you did something wrong", 2 means "the check could not run". Anything that cannot be verified must exit 2 — never report an unverifiable result as a pass.
  • The nav is hand-maintained in the static pages and in the nav() function of scripts/build_site.py. Change one without the other and generated log pages drift from the rest of the site (this exact desync was caught by Copilot review in a7301f2).
