Research log

living document · maintain by hand
scripts/build_site.py · content/log/ · log/ · feed.xml · sitemap.xml · llms.txt

Purpose

The research log at /log/ is the dated public journal of the volatility build: what you tried, what you expected, what happened, and what you had wrong — negative results included. Each entry gets its own URL on purpose: retrieval engines return passages, so an entry sharing a URL with twenty others cannot be cited on its own. Behind it sits scripts/build_site.py, the one script that turns hand-authored fragments into entry pages and regenerates everything derived — the log index, feed.xml, sitemap.xml, the log section of llms.txt, and every dateModified on the site. As of this writing the log has shipped no entries yet; the index renders a "No entries yet" pending state.

How it works

The fragment convention

An entry is a file in content/log/ named YYYY-MM-DD-a-short-slug.html — the filename stem becomes the URL (/log/<slug>.html). The file opens with a meta block: 

<!--meta
title: Short, specific title — state the finding, not the topic
date: 2026-09-01
stage: Surface construction
summary: One sentence that stands alone; it becomes the meta description, feed summary, and index card.
-->

title, date, and summary are required; stage is optional and renders as a badge. Lines starting with # are comments. The date must be ISO YYYY-MM-DD and not in the future. Everything after the block is the body: plain HTML (p, ul, h2, table, blockquote, code) — no h1, the page supplies one from the title. Parsing failures are hard exits (SystemExit with the filename), not warnings.

Slug rules, added in the 2026-09-02 audit: the slug must match [A-Za-z0-9._~-]+ (RFC 3986 unreserved characters — it is interpolated unescaped into URLs, HTML attributes, the Atom feed, and the sitemap), and index is reserved, because an entry with that slug would be silently overwritten by the index injection. Duplicate slugs are rejected.

The build pass

main() runs six steps. Entries are sorted newest-first by (date, slug) and each is rendered through ENTRY_TEMPLATE into log/<slug>.html: full page chrome, BlogPosting + BreadcrumbList JSON-LD, and a prev/next pager (older entry on the ← side, newer on the → side, "All entries" in the middle). datePublished is fixed at noon UTC of the entry date — the entry records a day, not a moment, and noon renders the same date either side of the date line. A "Last revised" line appears only when the fragment's last non-build commit is later than the entry date — same-day edits before first publication are not revisions.

Then the entry list is injected into log/index.html, the log section into llms.txt, feed.xml is rendered wholesale, timestamps are stamped into the six STATIC_PAGES, and the sitemap is rendered last so it sees the final entry list.

Markers and injection

Generated regions inside hand-authored files live between paired comments: <!-- BUILD:LOG-ENTRIES:START --> … <!-- BUILD:LOG-ENTRIES:END -->. The MARKER regex (build_site.py:74) matches any BUILD:<NAME> pair and inject() replaces the body of the named one; a missing marker is a hard fail. Note the name class is [A-Z-]+ — digits do not match, so a future BUILD:NAV2:START would never fire (audit item 10). Do not hand-edit anything between markers: the next build overwrites it. In particular the pending-state copy ("No entries yet") lives in render_log_index_list(), not in log/index.html — editing the HTML between the markers does nothing.

Dates come from git, never from your keyboard

Every lastmod and dateModified on the site is the committer date (%cI) of the last commit to touch the file, via last_modified(). A file git has never seen (a new entry previewed locally) falls back to the current time; a genuine git failure raises rather than silently stamping everything with the build time. The function is lru_cached — one git subprocess per path, since the feed and sitemap each ask for every entry's date again. Month names come from a fixed table, not strftime('%B'), because strftime follows the process locale and a non-English dev machine would desync the CI --check.

The fixed-point dance with CI

Stamping a date into a file changes the file, which changes its last-commit date, which demands another stamp — without an escape hatch the build never reaches a fixed point. The hatch is BUILD_COMMIT_SUBJECT = "chore: rebuild derived site metadata": commits with exactly that subject are excluded from the timestamp computation (--invert-grep). build-site.yml holds the other half of the contract: on pull requests it runs --check (exit 1 if anything derived is stale); on pushes to main it rebuilds and the bot commits with exactly that subject. A comment in the workflow warns: change the subject in one place without the other and the build chases its own tail. Locally, the pre-commit hook runs the build on every commit — it regenerates files but does not stage them, so the commit fails with "files were modified" until you re-add (audit item 46).

Orphan cleanup — destructive

After planning, the build globs log/*.html and deletes any file that is not index.html and not in the planned set. This is how a deleted fragment's page disappears — but it also means a hand-authored page dropped into log/ is destroyed without asking. Under --check the same files are reported as orphaned: and fail the build. Do not keep anything hand-written in log/. Audit item 11 proposes restricting deletion to files bearing a generated-by marker; until then, treat the directory as build-owned.

Zero-entry state

With no fragments, render_log_index_list() emits the .pending block ("No entries yet …"), the llms.txt section renders empty, and the feed's <updated> falls back to the lastmod of log/index.html. All three are live today — the pipeline has been exercised end-to-end by CI since 2026-08-23, just never with a real entry. Expect the first entry to surface rough edges nobody has hit yet; audit item 48 already flags one (the log-index footer has 3 links, generated entry pages have 6 — harmonise when the first entry ships).

Conventions and gotchas

  • Do not hand-edit log/<slug>.html, feed.xml, sitemap.xml, or anything between BUILD markers — the build owns them. log/index.html and llms.txt are hand-edited outside the markers only.
  • To add an entry: copy content/log/TEMPLATE.html.example, rename to YYYY-MM-DD-slug.html, write, run python3 scripts/build_site.py. The template's own comments carry the two content rules: every h2 section must pass the island test (quotable alone), and keep the numbers in.
  • --check is what CI runs. If it fails, run the build and commit the result — do not patch generated files by hand to make the diff go away.
  • stamp() silently no-ops if a page loses its stamp markers, and --check still passes (audit item 8). If a page's "last updated" stops moving, check its markers before blaming the build.
  • Entry titles are interpolated raw into Markdown in llms.txt — a [ or ] in a title breaks the link (audit item 9). Avoid brackets in titles until escaping lands.
  • The generated nav in nav() is a second copy of the site nav. It already drifted once (the GitHub external-link attributes, fixed in a7301f2) — when you change the header nav on the static pages, change it here too.
  • render_entry() escapes user text into HTML/JSON (esc, json_str with </ guarding), but the body HTML is injected verbatim — the fragment is trusted input. It is your own repo, but do not paste third-party HTML into a fragment.
  • Timestamps are committer dates with the contributor's offset (currently -06:00 sitewide). Audit item 49 questions how that reads for a New-York-based candidate; no decision taken yet.
