Purpose

The vol/ section is the public face of the trading system the whole site exists to support. Three pages: an overview that states the premise and shows the architecture with per-stage status labels, an evaluation protocol that was written and published before any results exist (that ordering is the point), and a build-status page that will host the live out-of-sample track record. The data file and the JavaScript behind that third page are the engineered heart of the section: an append-only record whose every statistic is recomputed in the reader's browser. As of this writing the system is in development and the record has zero observations — the page says "Tracking has not started", and that is the correct state, not a bug.

How the track record works end-to-end

One observation per trading day lands via python3 scripts/append_observation.py --date … --nav … --gross-pnl … --costs … --positions … --mode paper. The script validates the whole document and refuses to modify or reorder anything already present; with --commit each observation is its own dated commit, so git history is the timestamp trail. --mode-change live records a paper→live transition in mode_changes instead of appending a day.

In CI, validate_track_record.py --check-append-only diffs the file across the whole push range — not just HEAD against HEAD^, because a multi-commit push could otherwise smuggle a rewrite in an earlier commit — and fails closed (exit 2) if the baseline cannot be read. Immutable metadata (periods_per_year, mode_changes) is protected as well as the observations, since rescaling the annualisation factor would quietly change every derived statistic. None of this survives a force-push: never rewrite this repository's history.

In the browser, track-record.js fetches /data/track-record.json (with a 15-second abort timeout), validates and sorts it in normalise(), then derives everything from the returns implied by nav: cumulative and annualised return, annualised volatility, Sharpe, PSR, MinTRL, max and current drawdown, skew, kurtosis, cost share. Nothing is precomputed anywhere — the page cannot disagree with the data because the page is the data, computed at view time. Empty input renders the "Tracking has not started" state; the loading state is the default precisely so a no-JS reader is never told a falsehood.

Conventions and gotchas

  • MIN_RETURNS = 20. Inferential statistics (Sharpe, PSR, MinTRL, skew, kurtosis) are withheld until there are 20 daily returns — that is 21 observations, which is why the page hints say "Withheld under 21 observations". Descriptive numbers (cumulative return, drawdowns, costs) are always shown. This asymmetry is deliberate, not a rounding bug.
  • Sharpe is excess over a 0% risk-free rate, sample sd (ddof=1). Skewness and kurtosis are the biased sample moments g1/b2 matching scipy.stats with bias=True; kurtosis is raw, so normal = 3, not 0. Pandas defaults differ — do not "fix" the JS to match pandas.
  • PSR and MinTRL use the per-period Sharpe, never the annualised one, benchmark zero, one-sided at 95%, following Bailey & López de Prado (2012) eq. 7 and 12. MinTRL is reported in returns and shown against the actual count, so a too-short record says so in the verdict box rather than implying significance.
  • inception stays null until the first observation; the append script sets it. The JS ignores the field and takes inception from the first observation's date.
  • mode_changes records paper→live transitions and the equity chart draws each as a labelled vertical boundary, so simulated and real-capital stretches are never visually conflated. The hero badge reads off the latest observation's mode.
  • The JS sorts observations by date itself and throws on duplicates — so the page renders correctly even if the file's order is disturbed, but this also masks a validator bypass (see watch-outs below).
  • Days-live depends on the viewer's clock (inception → now, clamped at 1), not on the data. Two viewers in different timezones can legitimately see different numbers on the same day.
  • The error state has no retry. A failed fetch renders a terminal error line until a manual reload.
  • Do not hand-edit the "last updated" times or article:modified_time in the vol pages. build_site.py stamps them from git history; that is what the many "rebuild derived site metadata" commits in the log are. Hand-edits get overwritten and dirty the diff.
  • Guards against degenerate data exist for a reason: a relative sd floor and a MAX_PLAUSIBLE_SHARPE = 30 cap suppress statistics on a suspiciously smooth or extreme NAV series rather than displaying a Sharpe of 1014. Do not remove them when "cleaning up".

Watch-outs

The open issues for this section live in the 2026-09-02 audit. The ones that will bite first: track-record.js has no automated tests, the JS sort masks validator bypasses, days-live depends on the viewer's clock, and a failed fetch is terminal with no retry — see frontend JS items. Validator-side gaps (timezone semantics of "future", the --mode default after going live) are under data contract / validator, and the timestamp-stamping behaviour that dirties diffs is under CI / repo hygiene. And the standing rule from data/SCHEMA.md: the append-only guarantee dies with a force-push — never rewrite this repository's history.
